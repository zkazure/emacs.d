#+title: Emacs Configuration

From now on my Emacs configuration will be stable and reliable.

However, there is still a long way to go.

* Package management

The configuration follows [[https://github.com/purcell/emacs.d][Purcell's]] modular style: =init.el= loads
=lisp/init-*.el=.  Borg is the sole third-party package manager.  Borg itself
and 152 package drones are Git submodules under =borg/= (153 drones in total),
each pinned to an exact commit; =early-init.el= calls =borg-initialize= before
=init.el= loads.  The existing ignored =elpa/= directory is dormant
compatibility storage and is not part of startup or builds.

For a fresh clone, use Borg's bootstrap sequence.  It first makes the pinned
Borg source available, then initializes every drone at its recorded commit and
generates the required autoload and byte-code files:

#+begin_src sh
git clone <configuration-url> ~/.emacs.d
cd ~/.emacs.d
make bootstrap-borg
make bootstrap
#+end_src

If =borg/borg= is already initialized, =make bootstrap= is sufficient.  A
plain =git submodule update --init --recursive= checks out the sources but
does not run Borg's build step.

Use =M-x borg-assimilate= to add a package, =M-x borg-build= to regenerate a
drone after an intentional source update, and =make build= for the explicit
batch build.  Package updates are manual: choose and validate a commit in its
submodule, then commit the resulting gitlink.  Startup neither downloads nor
upgrades packages, and native JIT compilation remains disabled.

The bootstrap follows the [[https://github.com/emacscollective/borg/blob/main/docs/borg.org][Borg manual's seed pattern]]:
=Makefile= includes the drone's =borg.mk= when available and otherwise offers
=make bootstrap-borg=.  The historical configuration at commit =3cca64c=
informs the Borg command bindings; this configuration deliberately keeps
=borg/= as the drone directory through =.borgconfig= rather than moving pins
to the manual's default =lib/=.

Emacs 32 supplies =org=, =eglot= and =use-package= as built-ins.  =cmake-mode=
is a pinned drone.  System tools, Tree-sitter grammars, fonts, native-module
build dependencies and personal data remain outside Borg's scope.

Packages deliberately *not* assimilated:

- =eglot=, =flymake= and =jsonrpc= are provided by Emacs 32 itself.  The
  =elpa/= copies were shadow installs of older GNU ELPA releases, so their
  version now follows the Emacs release instead of a pin.
- =cask= is unused by this configuration and its package metadata records no
  commit, so it cannot be pinned offline.  It stays in the dormant =elpa/=.
- =elpa/gnupg/= is *not* a package: it is package.el's
  =package-gnupghome-dir= and holds GPG key material.  Never delete it.
- Drones that bundle optional integration files whose dependencies are absent
  (for example =evil=, =pdf-tools= or =org-pdftools= for =ghostel= and
  =org-noter=) are left as-is; those files are not loaded by this
  configuration.

* LilyPond

LilyPond support uses a user installation at
=~/.local/opt/lilypond-2.26.0=.  Install the official 2.26 archive there; its
=bin/lilypond= is preferred only by Emacs and its child processes.  When the
installation is absent, Emacs starts normally and reports that LilyPond is
unavailable.  Files ending in =.ly= and =.ily= load the bundled
=lilypond-mode= on demand.

Org Babel uses the same compiler; its PDF viewer and MIDI player commands are
configured as =xdg-open=.  Use =C-c '= to edit a source block in
=lilypond-mode= and =C-c C-c= to run it.  For example:

#+begin_example
#+begin_src lilypond :file scale.png
\version "2.26.0"
\relative c' { c d e f g a b c }
#+end_src
#+end_example

Change =:file scale.png= to =:file scale.pdf= for PDF output.
